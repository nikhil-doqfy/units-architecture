# Model correction — 2026-09-01

## What changed

The PRD and Architecture Spine originally modeled Finance's core accounting entity as a standalone **`Company`** model (own base_currency/fiscal_year/VAT), mapped 1:1 from `Unit` via a new **Unit-to-Company mapping table** (old FR-2).

Corrected to:

- **`PropertyManagmentCompany` ("PMC") IS the accounting entity, 1:1.** No separate Company model exists or is created.
- **New Finance-owned table: `FinancePMCProfile`** — holds only accounting-specific settings (base_currency, country, fiscal_year_start_month), keyed by a required `pmc_id` field holding the *value* of the existing `PropertyManagmentCompany.id` (not a cross-DB FK — Finance and units-backend are separate Django projects sharing one Postgres instance).
- **`Organization`** (existing units-backend model) sits one level above PMC: `Organization` → `PropertyManagmentCompany` → `Property` → `PropertyBlocks` → `Unit` (all existing, unmodified). One Organization can have multiple PMCs, each with independent books.
- **Old FR-2 (Unit-to-Company mapping) is dropped/retired**, not renumbered. `Unit` already resolves to its PMC via the existing `Unit.parent_property.pmc` chain — no new field or table is needed. The FR-2 slot is marked `[REMOVED]` in the PRD with a pointer to this resolution, so later FRs' historical references to "FR-2" stay traceable.
- **AD-19** (previously "Company maps to PMC via a direct pmc_id field") is rewritten in place (same id, not renumbered): its premise flips from "resolve a join between Company and PMC" to "`FinancePMCProfile.pmc_id` IS the primary key relationship, not a join to resolve." The JWT-payload-to-`UserProfile` bridge-helper half of AD-19 is unchanged and still required.
- **Organization-level consolidated reporting is explicitly deferred to Phase 2.** Phase 1 reporting (FR-10–FR-13) stays scoped strictly per-`FinancePMCProfile`. Summing across all PMCs under one Organization is a Phase 2 aggregation query, not a data model change, since `FinancePMCProfile.pmc_id` already anchors to the correct PMC.
- **units-frontend UI work is explicitly deferred to Phase 2.** Phase 1 ships the Finance backend and reporting API only, verified via Swagger/Postman/automated tests — no Angular screens. The PRD's existing UJ-1 (Owner/PMC checking Trial Balance in the UI) is a real, intended future journey, not removed from the document — just moved to Phase 2 scope.

## Why

User (Rahul) clarified the real domain model during epics/stories breakdown: "PMC is the Company here... don't modify existing table, create new ones and manage relations... One Organization → multiple PMCs → has multiple properties → has multiple blocks → has units." Confirmed via `AskUserQuestion`: PMC = Company 1:1, Organization is the roll-up level, new table should be named `FinancePMCProfile`, no new Unit mapping table (reuse `Unit.parent_property.pmc`), Organization roll-up and frontend UI both deferred to Phase 2.
